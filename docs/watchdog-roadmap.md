# Сторож на Agent SDK — дорожная карта

Статус: в работе. Обновляется по мере прохождения этапов.

## Зачем

`monitor.sh` умеет замечать, что что-то сломалось, но не умеет объяснять. Он шлёт
«Контейнер не запущен» и замолкает — дальше человек лезет на сервер и разбирается
сам. Сторож закрывает именно этот разрыв: он объясняет, что произошло, чем это
грозит, и предлагает починку кнопкой.

## Принцип

Детерминированный код собирает факты и решает, что изменилось. Модель просыпается
**только на дельте** — на смене состояния, а не по расписанию. Диск, третьи сутки
стоящий на 81%, молчит. Диск, ушедший с 80% на 91% за пять минут, будит модель.

Из этого следует главное свойство: в спокойный день сторож не тратит ни одного
токена и не шлёт ни одного сообщения.

## Поток

```
systemd timer (*/5 мин)
        │
        ▼
   collect ── детекторы, без LLM → facts.json
        │
        ▼
   delta   ── сравнение с прошлым снимком
        │
        ├── дельты нет → выход (0 токенов, 0 сообщений)
        │
        ▼ дельта есть
   deepen  ── детерминированный добор контекста под тип проблемы
        │     (упал юнит → его последние строки journalctl)
        ▼
   analyst ── Claude Agent SDK, подписка Max, READ-ONLY
        │     вход: дельта + факты + добранный контекст
        │     выход: severity, объяснение, набор действий из каталога
        ▼
   notify  ── @plgames_admin_bot → владельцу, с кнопками
        │
        ▼ владелец нажал кнопку
   remedy  ── исполнение ОДНОГО действия из каталога, с аудитом
```

## Модель безопасности

Инцидент с утечкой токена показал цену беспечности, поэтому границы жёсткие.

**1. Модель ничего не исполняет.** У аналитика нет `Bash`, `Write`, `Edit`.
Только `Read`/`Grep`, и только внутри каталога инцидента, куда наши же детекторы
положили факты. Read-only здесь — не обещание в промпте, а отсутствие инструмента.

**2. Модель не придумывает команды.** Она выбирает действия из фиксированного
каталога по идентификатору. Строку команды формирует наш код, не модель.

**3. Ничего не выполняется без человека.** Модель предлагает — владелец нажимает.
Автоматической починки нет ни в каком виде.

**4. Содержимое логов — это данные, а не инструкции.** В nginx и fail2ban пишут
посторонние: строки в логах сочиняет атакующий. Аналитик получает их как
недоверенный текст и предупреждён об этом в системном промпте. Поскольку
исполнять он всё равно ничего не может, инъекция в худшем случае портит совет.

**5. Разделение привилегий.** Бот работает под выделенным `tgbot` (не под `plg`:
у того беспарольный sudo на всё, и компрометация бота означала бы сразу root).
Сторож — под `plg`, потому что к нему привязаны credentials подписки. Общее у них
только группа `watchdog`: сторож пишет вердикты, бот их читает. Действия исполняет
отдельный root-хелпер, который заново проверяет идентификатор действия по каталогу
и игнорирует всё, что пришло сверх него. Доступ к хелперу — одна строка sudoers на
один скрипт, и она выдана только боту.

**6. Только владелец.** Бот отвечает исключительно на `OWNER_ID`; остальные
update'ы отбрасываются молча. Мультиарендный слой (регистрация чужих серверов,
выдача ключей в чат) убирается.

Каждый этап заканчивается коммитом и проверкой. Без прохождения проверки
следующий этап не начинается.

него. На этапе 6 добавлено не заложенное изначально подавление дребезга: без
него объект, циклящий crit→resolved, будил бы модель каждые пять минут.

## Каталог действий (этап 4)

Каталог намеренно узкий. Действие попадает в него, только если оно обратимо и
его последствия предсказуемы.

- `restart_unit` — рестарт systemd-юнита из белого списка
- `restart_container` — рестарт docker-контейнера из белого списка
- `prune_builder` — очистка docker build cache (главный пожиратель диска)
- `vacuum_journal` — усечение журнала systemd по времени
- `nothing` — «ничего не делать», фиксируется в аудите наравне с остальными

Удаление данных, правка конфигов, любые операции с сетью и SSH в каталог
не входят и входить не должны.

В фазе 11 добавлены ещё четыре — `start_container`, `reset_failed`,
`rotate_logs`, `renew_certs` — по правилу приёма, описанному там же.

## Что осознанно не делаем

- Автоматическую починку без человека.
- Произвольные shell-команды через бота — ни в каком виде, включая «только для
  владельца». Утечка токена не должна давать root.
- Дублирование детекторов: факты собираются рядом с `monitor.sh`, а не вместо
  него; текстовые алерты и резервные каналы ntfy/email остаются как есть.

## Хвосты аудита, закрытые после сторожа

Четыре пункта, оставшиеся от разбора инцидента с утечкой токена.

### Бот больше не равен root

У `plg` беспарольный sudo на всё, а бот читает update'ы из Telegram — то есть
является поверхностью атаки. В такой связке его компрометация означала root.

Бот переведён на системного `tgbot`, которому из sudo доступен ровно один
бинарник — исполнитель починок. Сторож остался под `plg`: ему нужны credentials
подписки, а наружу он не смотрит. Связывает их группа `watchdog` с setgid на
каталоге состояния. Изменяемые данные вынесены в `/var/lib/telegram-bot`, иначе
скомпрометированный бот мог бы переписать собственный код.

### Ключ агента больше не летит по сети

Агент отдаёт метрики по обычному HTTP, а клиент присылал сам ключ заголовком
`X-Secret-Key` — любой на пути трафика получал бессрочный доступ. TLS на
разбросанных серверах поднять не всегда возможно, поэтому убрана причина:
теперь уходит подпись HMAC от метода, пути, времени и разового числа
(`agent_auth.py`). Перехватчик получает подпись на две минуты для одного
запроса, повтор отбивается запомненным nonce.

Метрики по-прежнему идут открытым текстом — это меньшая ценность, чем ключ, но
порт 5000 всё равно стоит закрыть фаерволом.

### Удалённые серверы под наблюдением

Их не проверял никто: `monitor.sh` следит за локальной машиной, а
`monitor_remote.py` по устройству пропускал владельца. Теперь их опрашивает
сторож — двумя маршрутами, параллельно, с расшифровкой причины отказа.
`monitor_remote.py` удалён.

### Секреты ушли из crontab

Токены DuckDNS и `X-Cron-Secret` стояли прямо в строках `curl`, а аргументы
процесса читаются любым пользователем через `ps`. Секреты переехали в
`/home/plg/ops/*.env` (0600), cron зовёт обёртки, передающие их curl через
`-K <файл>`. Скрипты лежат в `/home/plg/ops`, вне этого репозитория; схема
описана в тамошнем README.

Заодно у старого `crontab-backup-20260829.txt` были права 0644 — с теми же
секретами внутри. Исправлено на 0600.

**Что стоит сделать владельцу:** эти токены долго были видны в `ps` и в
доступном на чтение бэкапе, поэтому их разумно перевыпустить.

# Этапы 8–11: сторож, который отвечает

> **Статус:** все четыре фазы сделаны 08.09.2026. Дорожная карта закрыта.

## Что не так сейчас

Аналитик — полноценный агент Claude, но канал до владельца шириной в три кнопки.
Весь разбор ужимается в заголовок, пять предложений и до четырёх вариантов —
и на этом разговор заканчивается. Спросить «почему?» нельзя.

Хуже с критом. Критичный инцидент — это **одно** сообщение. Не заметили ночью —
тишина: никто не напомнит, инцидент через 14 дней вычистится вместе с каталогом.
Аудит фиксирует нажатия, но молчание не отличается от «принял к сведению».

И разбирается крит той же моделью, что «контейнер моргнул»: `WATCHDOG_MODEL` —
Sonnet всегда. Для 95% случаев это правильная экономия общей подписки. Для
падения флагмана — нет.

## Фаза 8 — Диалог по инциденту ✅ сделано 08.09.2026

> Реализовано и проверено на живом происшествии. Ниже — как задумывалось;
> после раздела «Что вскрылось при реализации» описано, чем пришлось
> отличаться от плана.

Владелец отвечает на сообщение об инциденте (обычный reply в Telegram) или жмёт
кнопку «💬 Спросить». Аналитик перечитывает каталог того же инцидента и отвечает.

**Почему это безопасно и почему именно с этого начинаем.** Модель не получает
ни одного нового права: тот же `cwd=incident_dir`, те же `Read`/`Grep`/`Glob`,
тот же пустой `setting_sources`. Она получает только больше ходов. Пункты 1–4
модели безопасности не двигаются вообще — а польза наибольшая из всего списка.

Что нужно сделать правильно:

* **Привязка ответа к инциденту.** `notify.py` уже возвращает `message_id` —
  сейчас он выбрасывается. Сохранять в `message.json` рядом с вердиктом; бот
  ловит `filters.REPLY` и находит инцидент по `reply_to_message.message_id`.
* **Общая песочница одним куском.** Настройки `ClaudeAgentOptions` вынести в
  `watchdog/sandbox.py`, чтобы разбор и диалог не могли разойтись. Это прямой
  урок F1 из аудита 08.09.2026: три копии опроса агента — ровно то, из-за чего
  одна тихо осталась на старой схеме авторизации.
* **Бюджет.** Подписка общая с повседневной работой. Потолок вопросов на
  инцидент и на сутки, отказ вежливым текстом, а не молчанием.
* **Замок на инцидент.** Два вопроса подряд не должны запускать два аналитика
  на один каталог.
* **Ответ модели экранируется.** Он идёт в HTML и составлен по содержимому
  логов, куда пишет атакующий. См. F3 того же аудита.
* **Инцидент мог устареть.** Reply на сообщение двухнедельной давности отвечает
  «инцидент удалён», а не падает: `IncidentError` для этого уже есть.
* **Долгий ответ.** Модель думает десятки секунд — слать `typing`, ответ
  отдельным сообщением в ту же ветку.

История диалога — `dialogue.jsonl` в каталоге инцидента, рядом с `choices.jsonl`.

**Проверка фазы:** вопрос по реальному инциденту получает осмысленный ответ;
попытка вопросом заставить модель что-либо выполнить отбита отсутствием
инструмента; превышение бюджета даёт отказ, а не тишину.

### Что вскрылось при реализации

План был верен по существу, но два предположения оказались ложными, и оба
нашлись только на живой машине.

**1. Бот не может позвать модель. Вообще.** Аналитик работает под `plg`, потому
что к нему привязана подписка Claude, а бот — под `tgbot`: `.credentials.json`
имеет права 600 и владельца `plg`, а у `tgbot` вдобавок `HOME=/nonexistent`.
Прямой вызов `converse.ask()` из бота был бы мёртвым кодом.

Очевидное решение — `sudo -u plg` для бота — здесь неприемлемо: у `plg`
беспарольный sudo на всё, то есть «стать plg» тождественно «стать root». Ровно
от этого бота и отделяли в этапе про выделенного пользователя.

Поэтому вопрос и ответ ходят файлами через каталог `/var/lib/watchdog/ask/`,
общий по группе `watchdog`, а модель зовёт отдельная служба `watchdog-ask`
под `plg`. Через границу идёт только текст; идентификатор происшествия служба
перепроверяет своей же строгой проверкой формы. Права нигде не пересеклись.

**2. Каталог обмена обязан быть плоским.** `PathExistsGlob` в systemd следит
только за тем уровнем, где стоит шаблон. Заявку в
`incidents/<id>/ask.request` служба не замечала вовсе — проверено; тот же файл
уровнем выше запускал её мгновенно.

**3. Попутно нашлась поломка, которая была всё это время.** Каталоги инцидентов
создавались `os.makedirs(mode=0o770)`, а режим там режется umask — под systemd
он `0022`, и каталоги получались `2750`, без записи для группы. Значит
`record_choice()` не мог записать ничего, а его `except OSError: pass` это
скрывал: **аудит нажатий владельца был пуст всё время существования сторожа**.
Проверено — ни одного `choices.jsonl` на диске не было.

Исправлено в трёх слоях: явный `chmod` после `makedirs` (chmod umask не режет),
`UMask=0002` в юнитах, и снятое молчание в `record_choice` — теперь неудача
записи попадает в журнал.

## Фаза 9 — Дожим до ответа ✅ сделано 08.09.2026

> Реализовано в `watchdog/followup.py`, проверено на живой машине.
> Ниже — как задумывалось; отличия описаны после раздела «Проверка фазы».

У инцидента появляется состояние: `new` → `acknowledged` (нажата любая кнопка
или задан вопрос) → `closed` (объект вернулся в норму по дельте). Половина
механизма уже есть: `choices.jsonl` пишется, включая «ничего не делать».

Пока критичный инцидент в `new`, сторож напоминает с растущей паузой:
10 мин → 30 мин → 1 ч → каждые 3 ч, не более шести раз, потом сообщает, что
перестаёт напоминать. В напоминании — сколько времени прошло и **сдвинулось ли
что-нибудь** («диск ушёл с 94% на 96%», «контейнер поднялся сам»).

Дожим прекращается по любому из: подтверждено, поломка ушла, исчерпан лимит.

> **Известное ограничение, принятое сознательно.** Напоминания идут тем же
> каналом, что и первое сообщение. Telegram у провайдера доступен только через
> мост на `127.0.0.1:18443` — если отвалится он или сеть, не придёт ни исходное
> сообщение, ни один дожим. Запасной канал (ntfy/email) в `monitor.sh` уже
> обвязан, сторож его не использует; включение отложено по решению владельца.
> Вернуться к этому стоит после первого же случая, когда сообщение не дошло.
>
> Отдельно: при по-настоящему умирающей машине (диск 100%, OOM) сторож может
> не запуститься вовсе. Более грубый, но живучий путь — пятиминутный
> `monitor.sh` из root-крона; он остаётся именно поэтому.

**Проверка фазы:** крит без реакции даёт напоминания по расписанию и замолкает
после подтверждения; поднявшийся сам объект закрывает инцидент без участия
владельца.

### Что вскрылось при реализации

**1. Признак «отреагировал» не понадобилось хранить.** По плану у инцидента
появлялось состояние, которое кто-то должен записывать. Но следы уже есть:
`choices.jsonl` (нажатие, включая «ничего не делать») и `dialogue.jsonl`
(вопрос аналитику). Оба пишет бот, дожим их только читает — и второй писатель
через границу прав `tgbot`/`plg` не потребовался вовсе. Признак «закрылось
само» точно так же берётся из снимка сторожа, а не из нового опроса системы:
два источника правды разошлись бы ровно в тот момент, когда это важнее всего.

**2. Событиям понадобился адрес.** Чтобы сказать «диск ушёл с 94% на 96%», надо
знать, где смотреть значение, а по паре «вид + имя» это восстанавливается
неоднозначно: у памяти два разных числа с одинаковыми видом и ключом.
`delta.py` теперь кладёт в событие `slot` (адрес в снимке) или `list_field`
(для того, что живёт списком, — упавших юнитов и вставших контейнеров).
Разбирать адрес по точкам нельзя: внутри адреса сайта и сертификата сидит URL.

**3. Живые данные добавили правило, которого не было в плане.** К моменту
включения на диске лежали два крита с прошлой ночи — и дожим начал бы
напоминать о них задним числом, по шесть раз о том, что владелец уже знает.
Инцидент, который к первому взгляду старше всего расписания, закрывается
молча. Это та же защита, что базовый снимок в `delta.py`, только от
накопленного за ночь, а не за годы.

**4. Дожим стоит за конвейером, а не в нём.** Напоминать надо ровно в те тихие
проходы, когда дельты нет, — то есть когда конвейер заканчивается на
`analysed: false`. Поэтому `run.sh` запускает его отдельной командой и не даёт
сбою доставки оборвать проход.

Проверено на живой машине: свежий крит дал напоминание веткой к исходному
сообщению, повторный проход в ту же минуту промолчал, нажатие кнопки закрыло
дожим навсегда, а два настоящих ночных крита получили пометку «просрочен» и не
дали ни одного сообщения. 30 тестов.

## Фаза 10 — Сильная модель на крите ✅ сделано 08.09.2026

`WATCHDOG_MODEL` остаётся Sonnet. Добавляется `WATCHDOG_MODEL_CRIT` (по
умолчанию Opus), который берётся **только** когда в дельте есть событие
`crit` — и только для первого разбора инцидента. Уточняющие вопросы (фаза 8)
остаются на Sonnet, пока владелец явно не попросит разобраться глубже.

Ограничитель обязателен: суточный потолок разборов на сильной модели, иначе
дребезжащий крит выест подписку. Подавление дребезга из `delta.py` тут работает
на нас, но одного его мало.

**Проверка фазы:** крит разбирается сильной моделью, warn — прежней; при
исчерпании суточного потолка разбор идёт на Sonnet с пометкой, а не пропадает.

### Что вскрылось при реализации

Выбор модели был написан ещё в фазе 3, но молчал о себе: при исчерпании
потолка разбор просто уезжал на обычную модель, и отличить его от усиленного
было нельзя ни в вердикте, ни в сообщении. Владелец поверил бы слабому разбору
ровно так же, как сильному, — тихая деградация худшего вида. Теперь решение
возвращается целиком (какая модель, поднята ли, исчерпан ли потолок), ложится
в `meta` вердикта, и в уведомлении появляется пометка.

Счётчик увеличивается **до** разбора: разбор может не дойти до конца, но
ресурсы потратит те же. Модели вынесены в юнит явными переменными — раньше они
жили только значениями по умолчанию в коде, и «поменять модель в юните» из
документации было нечем.

19 тестов; заодно закрыт разбор ответа модели, до сих пор не покрытый вовсе:
ограда, предисловие, вложенные скобки, действие не из каталога, пропущенная
цель, больше четырёх вариантов.

## Фаза 11 — Осторожное расширение каталога ✅ сделано 08.09.2026

Главное здесь не список, а правило. **Действие попадает в каталог, только если
выполнены все условия:**

1. обратимо, последствия предсказуемы;
2. цель проверяется дважды — формой (regex) и живым состоянием прямо сейчас;
3. команду собирает наш код, модель называет только идентификатор;
4. ничего про ssh, сеть, пользователей, конфиги и удаление данных;
5. есть тест на **отказ**, как у существующих в `test_catalog.py`.

Четыре кандидата, отобранные под реальный инвентарь этой машины (64 контейнера,
compose-проекты, 19 сертификатов Let's Encrypt):

| Действие | Что делает | Чем ограничено |
|---|---|---|
| `start_container` | поднять остановленный контейнер | только если контейнер сейчас stopped и не в `DOCKER_IGNORE`. Именно `docker start`, а **не** `compose up`: последний умеет тянуть образы и пересоздавать — это уже другой класс полномочий |
| `reset_failed` | снять с юнита флаг failed | только если юнит сейчас failed и не в `UNIT_DENY`. Чистая бухгалтерия: даёт юниту снова попробовать по своей же политике рестарта |
| `rotate_logs` | `logrotate -f` | без цели вообще. Взято вместо «усечь лог»: у того целью был бы путь от модели, а ротация — штатный механизм, и логи не теряются |
| `renew_certs` | `certbot renew` | без цели, идемпотентно. Закрывает реальный случай: сертификат застрял ниже 30 дней — значит автопродление сломалось |

Три из четырёх не принимают цель вообще — это не совпадение, а отбор: действие
без цели невозможно направить не туда.

**Проверка фазы:** каждое действие отвергается, когда живое состояние его не
оправдывает; каждый отказ виден в `/var/log/watchdog-remedy.log`.

### Что вскрылось при реализации

Живой инвентарь исправил каталог дважды, оба раза до первого нажатия кнопки.

**1. Разовые задачи выглядят как поломки.** `svod-migrate-1` — миграция базы,
завершившаяся `Exited (0)` шесть дней назад. По первоначальному условию
(«контейнер сейчас stopped») каталог поднял бы её повторно, а прогнать
миграцию второй раз — не «обратимо с предсказуемыми последствиями». Контейнер,
вышедший с кодом 0, не сломался, а закончил. После этой правки у
`start_container` на этой машине не осталось ни одной законной цели — и это
правильный результат, а не признак ошибки.

**2. Отказ формулировал неправду.** Про остановленный контейнер он говорил
«сейчас не остановлен». Это тот же дефект, что в тот же день стоил ложного
диагноза «у агента не настроен ключ»: диагноз, собранный кодом, владелец
принимает за факт, и проверить его неоткуда. Отказ теперь различает
«работает», «завершился сам с кодом 0» и «такого контейнера нет».

**3. Политика для root не должна жить в домашнем каталоге.** Список
контейнеров-исключений каталогу нужен, но `monitor.local.conf` правится
владельцем, а `catalog.py` исполняется от root. Значение переносит `install.sh`
в `/etc/watchdog-remedy.conf`, так что источник правды один, а политику задаёт
файл, который меняется шагом установки.

**4. Продлению мал общий потолок.** 25 доменов, обход к внешнему сервису по
каждому: у действия появился собственный потолок времени, и вместе с ним
поднят потолок ожидания исполнителя.

Проверено через настоящий `sudo` и root-исполнителя: одиннадцать отказов и два
разрешения — `reset_failed` на нарочно уронённом юните (создан и тут же
удалён) и `renew_certs`, отработавший вхолостую, поскольку до ближайшего
истечения 33 дня. Все четырнадцать вызовов, включая отказы, лежат в аудите с
именем вызвавшего. `rotate_logs` проверен только на отказе: принудительная
ротация всех логов среди дня — настоящее изменение системы, и делать его ради
галочки незачем.

28 тестов каталога.

## Что по-прежнему осознанно не делаем

К прежнему списку добавляется одно, и именно из-за фазы 8:

* **Диалог не становится пультом.** Как только сторож начинает отвечать словами,
  появляется соблазн: «раз он понимает, пусть и выполняет, что попрошу».
  Нет. Разговор — read-only, изменения — только через каталог и только кнопкой.
  Иначе компрометация одного аккаунта Telegram даёт root на машине, где живут
  ~25 проектов, и никакой SSH для этого не понадобится.
