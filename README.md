# PLGames Admin

Админский Telegram-бот: состояние центрального сервера, всей инфраструктуры на
нём и удалённых серверов — с проактивными алертами и починкой по кнопке.

> Каталог проекта пока называется `telegram-server-bot`. Порядок безопасного
> переименования (пути зашиты в трёх systemd-юнитах и root-кроне) —
> в [`docs/rename-checklist.md`](docs/rename-checklist.md).

## Что показывает бот

```
🏠 Главное меню
├── 🖥 Этот сервер          диск, память, процессор, температура, здоровье дисков
├── 🌐 Инфраструктура       сводка + разделы:
│      🐳 Контейнеры   ⚙️ Службы   🔗 Сайты   🔒 Сертификаты   🛡 Безопасность
├── 🗂 Удалённые серверы    те, где установлен агент
└── 🔔 Алерты и пороги      что присылать и при каких значениях
```

Разделы «Этот сервер» и «Инфраструктура» читают последний снимок сторожа
(`/var/lib/watchdog/state.json`, обновляется каждые 5 минут). Своих измерений
бот не делает: он работает под `tgbot`, у которого нет ни доступа к docker, ни
sudo, — и выдавать их процессу, смотрящему в интернет, ради одной кнопки не
стоит. Центральному серверу поэтому не нужен ни агент, ни открытый порт.

Сообщения пишутся словами, а не только цифрами: не «swap 80%», а «подкачка
занята на 80% — памяти не хватает, система выгружает процессы на диск».

## Спросить сторожа

На любое сообщение о происшествии можно **ответить реплаем** — и задать вопрос:
«почему упало?», «это уже было?», «что смотреть руками?». Аналитик перечитает
материалы этого происшествия и ответит в ту же ветку.

Новых полномочий у модели при этом нет: тот же каталог происшествия, те же
`Read`/`Grep`/`Glob`. Разговор не пульт — изменить что-либо по-прежнему можно
только кнопкой, через каталог действий и root-исполнителя.

Вопрос и ответ ходят файлами через `/var/lib/watchdog/ask/`, а модель зовёт
служба `watchdog-ask` под `plg`: у бота нет credentials подписки, и выдавать их
ему нельзя — «стать plg» на этой машине означает «стать root».

## Кто о чём докладывает

`monitor.sh` и сторож раньше следили за одним и тем же и присылали по два
сообщения о каждой поломке, в двух форматах. Теперь роли разведены:

| | Докладывает |
|---|---|
| **Сторож** | всё, что умеет объяснить: диск, память, процессор, службы, контейнеры, сайты, сертификаты, SMART, удалённые серверы |
| **`monitor.sh`** | только то, чего сторож не видит: видеокарта, массовые баны, служба в `inactive` (а не `failed`), сертификаты доменов вне списка эндпоинтов |

Плюс `monitor.sh` — страховка: если снимок сторожа не обновлялся 15 минут, он
сообщает об этом и снова начинает докладывать обо всём сам. Он простой и живёт
в root-кроне, поэтому работает тогда, когда сложный сторож уже не может.

## Архитектура

| Компонент | Где работает | Назначение |
|-----------|--------------|------------|
| `bot.py` | центральный сервер | Telegram-бот: экраны состояния, серверы, алерты, кнопки починки |
| `infra.py` | центральный сервер | Чтение снимка сторожа и человеческие формулировки для экранов |
| `agent.py` | на каждом наблюдаемом сервере | Flask/Gunicorn API `:5000/status` — отдаёт метрики (CPU/RAM/диск/GPU) |
| `monitor.sh` | центральный сервер, cron `*/5` | Проактивный мониторинг **локального** сервера и всех его проектов (Docker, systemd, HTTP, SMART, SSL). Алерты — владельцу |
| `agent_auth.py` | обе стороны | Подпись запросов к агенту: секрет не передаётся по сети |
| `watchdog/` | центральный сервер, systemd-таймер `*/5` | Сторож: замечает изменения (включая удалённые серверы), разбирает их моделью, присылает варианты кнопками, отвечает на вопросы и напоминает о крите без ответа |

Данные: `users.json` (серверы пользователей), `monitor_subscribers.json` (подписки/пороги) — оба в `.gitignore`.

## Установка бота

```bash
git clone <repo> && cd telegram-server-bot
python3 -m venv venv
venv/bin/pip install -r requirements.txt
```

Секреты живут **только** в env-файле вне репозитория:

```bash
sudo install -m 600 -o root -g root /dev/null /etc/telegram-server-bot.env
sudo tee /etc/telegram-server-bot.env >/dev/null <<'EOF'
TELEGRAM_TOKEN=<токен от @BotFather>
OWNER_ID=<ваш Telegram id>
EOF
```

В `config.py` и в репозитории секретов нет и быть не должно: `config.py` только
читает окружение, а файл — лишь если он доступен (то есть под root, для
`monitor.sh`). Боту переменные отдаёт systemd, не открывая процессу сам файл.

### systemd-сервис бота

```ini
# /etc/systemd/system/telegram-server-bot.service
[Service]
User=plg
WorkingDirectory=/home/plg/telegram-server-bot
EnvironmentFile=/etc/telegram-server-bot.env
ExecStart=/home/plg/telegram-server-bot/venv/bin/python bot.py
Restart=always
```

Бот отвечает только владельцу (`OWNER_ID`); остальные update'ы отбрасываются
молча. Без `OWNER_ID` он не стартует.

### cron для проактивного монитора

```cron
*/5 * * * * /home/plg/telegram-server-bot/monitor.sh
```

Без этой строки алерты **не приходят** — `monitor.sh` не запускается сам.

## Установка агента на наблюдаемый сервер

Нужна только для **удалённых** серверов: центральный наблюдается через сторожа.

В боте: «Удалённые серверы» → выбрать сервер → «Как установить агента». Команда
вида:

```bash
SECRET_KEY=<КЛЮЧ> bash <(wget -qO- https://raw.githubusercontent.com/Leonid1095/SYSadmins-BOT/main/install.sh)
```

> 🔑 Ключ передаётся **переменной окружения**, а не аргументом. Аргументы
> процесса лежат в `/proc/<pid>/cmdline` и читаются любым пользователем машины:
> с `--key` ключ агента было видно в обычном `ps` всё время установки.
> `--key` ещё принимается ради старых инструкций, но предупреждает.

Агент ставится как `bot-agent.service` под отдельным пользователем `botagent`,
слушает `:5000` и принимает только **подписанные** запросы: клиент шлёт
HMAC-подпись от метода, пути, времени и разового числа, а не сам ключ.
Перехват трафика даёт подпись, годную на две минуты для одного запроса; повтор
отбивается запомненным nonce.

> ⚠️ Сами метрики по-прежнему идут открытым текстом. Это менее ценно, чем ключ
> с бессрочным доступом, но порт 5000 всё равно стоит закрыть фаерволом на IP
> центрального сервера.

> ⚠️ Агенты старее этой версии ждут `X-Secret-Key` и после обновления бота
> перестанут отвечать. Переустановите их той же командой.

## Что мониторит monitor.sh

- **Ресурсы**: диск `/`, HDD бэкапов, RAM, SWAP, CPU (утилизация + load average), GPU (темп./нагрузка)
- **Все проекты автоматически**:
  - все Docker-контейнеры — алерт, если не `running` или `unhealthy`
  - все systemd-юниты в состоянии `failed` + список критичных сервисов
  - HTTP-эндпоинты из `monitor.local.conf` (алерт при 000/5xx)
- **Железо/безопасность**: SMART диска, массовые баны fail2ban, истечение SSL

Пороги и цели настраиваются в `monitor.local.conf` (см. `monitor.local.conf.example`).

## Мониторинг нескольких серверов (Вариант A)

На каждом дополнительном сервере выполните под root одну команду — она поставит
`monitor.sh` в `/opt/server-monitor` и добавит cron `*/5`:

```bash
wget -qO- https://raw.githubusercontent.com/Leonid1095/SYSadmins-BOT/main/install-monitor.sh \
  | sudo bash -s -- --token <ТОКЕН> --owner <ВАШ_TG_ID>
```

С резервным каналом **ntfy** (доставка, когда Telegram недоступен):

```bash
wget -qO- https://raw.githubusercontent.com/Leonid1095/SYSadmins-BOT/main/install-monitor.sh \
  | sudo bash -s -- --token <ТОКЕН> --owner <ID> --ntfy-url http://<ntfy> --ntfy-topic server-alerts
```

Каждый сервер мониторит себя целиком (Docker/сервисы/SSL/нагрузка) и шлёт алерты во все
настроенные каналы. Пороги и эндпоинты — в `/opt/server-monitor/monitor.local.conf`.

## Сторож (`watchdog/`)

`monitor.sh` умеет заметить поломку, но не умеет объяснить. Сторож закрывает
именно это: он присылает разбор и варианты действий кнопками.

```bash
venv/bin/pip install claude-agent-sdk
sudo ./watchdog/install.sh
```

Как устроено:

```
таймер */5 → collect (детекторы) → delta (что изменилось)
           → [дельты нет? выход, ноль токенов]
           → deepen (добор контекста) → analyst (модель) → уведомление с кнопками
           → followup (дожим) — идёт всегда, даже когда дельты нет
```

Сторож следит и за удалёнными серверами владельца: опрашивает их агентов
подписанными запросами, пробуя прямой путь и, если он закрыт, обходной через
прокси, — и сообщает, каким именно маршрутом ответ пришёл. Прежний
`monitor_remote.py` удалён: он по устройству пропускал владельца, то есть как
раз его серверы и не проверял.

Модель просыпается **только на смене состояния**. Диск, третьи сутки стоящий на
81%, молчит; ушедший с 80% на 91% — будит. В спокойный день сторож не тратит
ни токена и не шлёт ни сообщения.

Крит, оставшийся без ответа, не тонет в тишине: напоминание уходит через
10 мин, 30 мин, час и дальше каждые три часа, не больше шести раз. В нём видно,
сдвинулось ли что-нибудь («было 94%, сейчас 96%»), и те же кнопки действий.
Напоминания прекращаются, как только владелец нажал кнопку или задал вопрос, —
или объект вернулся в норму сам.

На ответ можно ответить: реплай на сообщение об инциденте — это вопрос
аналитику, он перечитывает материалы и отвечает в ту же ветку. Новых прав у
модели при этом ноль.

Работает на подписке Claude (Agent SDK), API-ключ не нужен. Модель по умолчанию
`claude-sonnet-5` — меняется переменной `WATCHDOG_MODEL` в юните.

Границы: у аналитика нет `Bash`, `Write` и сети — только чтение файлов каталога
инцидента. Действия он не сочиняет, а выбирает из каталога (`watchdog/catalog.py`)
по идентификатору; команду собирает код. Ничего не выполняется без нажатия
владельцем, и каждое исполнение проходит через root-хелпер, который проверяет
заявку заново. Подробности и обоснования — в `docs/watchdog-roadmap.md`.

| Где смотреть | Что |
|---|---|
| `journalctl -u watchdog.service` | ход проверок |
| `/var/lib/watchdog/incidents/` | факты, контекст и вердикт по каждому инциденту |
| `/var/log/watchdog-remedy.log` | аудит починок, включая отклонённые |
| `<инцидент>/choices.jsonl` | что выбрал владелец, включая «ничего не делать» |
| `<инцидент>/dialogue.jsonl` | вопросы владельца и ответы аналитика |
| `<инцидент>/followup.json` | учёт напоминаний и состояние инцидента |

Обычный разбор идёт на Sonnet, настоящий крит — на модели сильнее, но не чаще
`WATCHDOG_CRIT_PER_DAY` раз в сутки; при исчерпании потолка разбор не
пропадает, а уходит на обычную модель с явной пометкой в сообщении.

Тесты (167): `venv/bin/python` на `watchdog/test_delta.py`,
`test_catalog.py`, `test_analyst.py`, `test_followup.py`, `test_converse.py`,
`test_bot_guard.py`, а в корне — `test_agent_auth.py` и `test_bot_ui.py`.

Всего 103 теста. `test_bot_ui.py` закрывает конкретные находки аудита: секрет не
уходит по сети ни из одного места, текст вердикта модели экранируется, порог из
нажатия проверяется, экраны не ломаются на пустых и враждебных данных, а пороги
бота совпадают с порогами сторожа.

## Безопасность

- Секреты — только в env-файле вне репозитория (0600 root), не в `config.py`.
- Бот отвечает исключительно владельцу; посторонние update'ы отбрасываются.
- Агент принимает только подписанные запросы; сам ключ по сети не ходит.
- Бот принимает только публичные IPv4 (защита от SSRF во внутреннюю сеть).
- Сторож не исполняет ничего сам: модель предлагает, владелец подтверждает,
  root-хелпер перепроверяет и ведёт аудит.
- Разметка сообщений — HTML, и всё подставляемое экранируется: имена
  контейнеров, домены и текст вердикта модели приходят из недоверенных мест.

Отчёты аудита (`docs/security-audit-*.md`) намеренно **не коммитятся**: они
перечисляют слабые места админского контура вместе с адресами серверов, а
репозиторий публичный. Последний разбор — 08.09.2026, лежит локально рядом
с проектом.
